# ПРОМТ: Инициализация проекта по методологии GRACE

**ЦЕЛЬ:** Инициализировать новый проект, следуя методологии GRACE (Graph-RAG Anchored Code Engineering). Создать минимальную, но полную структуру файлов, содержащую правила, контракты и шаблоны для дальнейшей AI-разработки.

**КОНТЕКСТ:** Проект начинается с нуля. Задача — заложить архитектурный "скелет", который будет служить единственным источником истины для всех последующих ИИ-сессий. Код генерируется на основе скелета, а не наоборот.

---

## ПЛАН ДЕЙСТВИЙ

1. Создать структуру папок:
   ```
   docs/
   docs/decisions/
   src/
   tests/
   ```
2. В `docs/` создать: `requirements.xml`, `technology.xml`, `development-plan.xml`, `verification-plan.xml`, `knowledge-graph.xml`, `session-log.md`, `glossary.md`.
3. В `docs/decisions/` создать `ADR-000-project-init.md`.
4. В корне создать: `AGENTS.md`, `rules.md`, `README.md`, `.gitignore`.
5. В `src/` создать файл-пример с MODULE_CONTRACT, в `tests/` — соответствующий тест.
6. Заполнить файлы содержимым, указанным ниже.
7. Сделать первый коммит: `init: GRACE project skeleton`.

---

## СОДЕРЖАНИЕ ФАЙЛОВ

### 1. `docs/requirements.xml`
*Назначение: "ЧТО" мы строим. Каждый use case имеет критерии приёмки — без них задача не может считаться завершённой.*

```xml
<?xml version="1.0" encoding="UTF-8"?>
<requirements>
  <project_name>НАЗВАНИЕ_ПРОЕКТА</project_name>
  <goal>КЛЮЧЕВАЯ_ЦЕЛЬ_ПРОЕКТА</goal>
  <use_cases>
    <use_case id="UC-1" priority="high">
      <name>Название варианта использования</name>
      <description>Что пользователь хочет достичь</description>
      <actor>Пользователь или система</actor>
      <acceptance_criteria>
        <criterion>Проверяемое условие 1</criterion>
        <criterion>Проверяемое условие 2</criterion>
      </acceptance_criteria>
    </use_case>
  </use_cases>
  <non_functional>
    <requirement type="performance">Например: ответ API &lt; 200 мс</requirement>
    <requirement type="security">Например: пароли только в хешированном виде</requirement>
    <requirement type="constraint">Например: работа офлайн</requirement>
  </non_functional>
</requirements>
```

### 2. `docs/technology.xml`
*Назначение: "НА ЧЁМ" мы строим и КАК запускаем инструменты. Агент не должен гадать, какой командой запустить тесты.*

```xml
<?xml version="1.0" encoding="UTF-8"?>
<technology>
  <runtime>НАПРИМЕР: Python 3.11+ / Node.js 20+</runtime>
  <language>ОСНОВНОЙ_ЯЗЫК</language>
  <framework>ОСНОВНОЙ_ФРЕЙМВОРК</framework>
  <key_libraries>
    <library purpose="назначение">Библиотека 1</library>
  </key_libraries>
  <tooling>
    <test_command>НАПРИМЕР: pytest tests/ -v</test_command>
    <lint_command>НАПРИМЕР: ruff check src/</lint_command>
    <format_command>НАПРИМЕР: ruff format src/</format_command>
    <run_command>НАПРИМЕР: python -m src.main</run_command>
  </tooling>
</technology>
```

### 3. `docs/development-plan.xml`
*Назначение: "КАК" структурирована разработка. Содержит только план и статусы. Описание модулей (пути, зависимости, контракты) живёт ТОЛЬКО в `knowledge-graph.xml` — здесь только ссылки по ID.*

```xml
<?xml version="1.0" encoding="UTF-8"?>
<development_plan>
  <!-- Статусы: planned | in_progress | done | blocked -->
  <phases>
    <phase id="P-1" status="planned">
      <name>Название фазы</name>
      <description>Описание работ</description>
      <tasks>
        <task id="T-1" module_ref="M-1" status="planned">
          <description>Что нужно сделать</description>
          <implements>UC-1</implements>
        </task>
      </tasks>
    </phase>
  </phases>
</development_plan>
```

### 4. `docs/verification-plan.xml`
*Назначение: "КАК" мы проверяем результат. Каждый тест трассируется до use case.*

```xml
<?xml version="1.0" encoding="UTF-8"?>
<verification_plan>
  <test_strategy>
    <principle>TDD 2.0: сначала агент пишет падающий тест, потом код.</principle>
    <framework>ТЕСТОВЫЙ_ФРЕЙМВОРК</framework>
    <coverage_target>80</coverage_target>
  </test_strategy>
  <test_suites>
    <suite id="TS-1" module_ref="M-1">
      <path>tests/test_main.py</path>
      <verifies>UC-1</verifies>
    </suite>
  </test_suites>
  <traces>
    <trace name="trace_example">
      <description>Лог-маркеры для отслеживания ключевого сценария</description>
      <markers>
        <marker>START: user_login_flow</marker>
        <marker>CHECK: user_credentials</marker>
        <marker>END: user_login_flow</marker>
      </markers>
    </trace>
  </traces>
</verification_plan>
```

### 5. `docs/knowledge-graph.xml`
*Назначение: ЕДИНСТВЕННОЕ место описания структуры проекта — модули, пути, зависимости. Все остальные документы ссылаются на модули только по ID.*

```xml
<?xml version="1.0" encoding="UTF-8"?>
<knowledge_graph>
  <project_name>НАЗВАНИЕ_ПРОЕКТА</project_name>
  <modules>
    <module id="M-1" status="planned">
      <name>Имя_модуля</name>
      <path>src/main.py</path>
      <purpose>Краткое назначение модуля</purpose>
      <test_path>tests/test_main.py</test_path>
      <cross_links>
        <cross_link target="M-0" type="depends_on" />
        <!-- Типы: depends_on | provides_to | implements_uc -->
      </cross_links>
    </module>
  </modules>
</knowledge_graph>
```

### 6. `docs/session-log.md`
*Назначение: Память между сессиями. Первое, что читает агент. Обновляется в конце каждой сессии.*

```markdown
# Журнал сессий

## Формат записи
Каждая сессия добавляет запись СВЕРХУ по шаблону.

---

## [ДАТА] Сессия N
- **Сделано:** ...
- **В работе (не завершено):** ...
- **Известные проблемы:** ...
- **Следующий шаг:** ...

---

## [ДАТА ИНИЦИАЛИЗАЦИИ] Сессия 0
- **Сделано:** Инициализация скелета проекта по GRACE.
- **Следующий шаг:** Заполнить requirements.xml реальными требованиями.
```

*Назначение: Единый словарь доменных терминов. Снижает разнобой в наименованиях.*

| Термин | Определение | Имя в коде |

### 8. `docs/decisions/ADR-000-project-init.md`
*Назначение: Записи архитектурных решений (ADR). Защищают осознанные решения от "улучшений" в будущих сессиях.*

```markdown
# ADR-000: Инициализация проекта по методологии GRACE

- **Статус:** принято
- **Дата:** [ДАТА]

## Контекст
Проект разрабатывается совместно с LLM в многосессионном режиме.

## Решение
1. Используется методология GRACE: контракты → код.
2. Формат документации — XML: строгая структура, однозначный парсинг для LLM, возможность валидации.
3. `knowledge-graph.xml` — единственное место описания структуры проекта.

## Последствия
- Больше токенов на документацию, но меньше расхождений между сессиями.
- Любое изменение архитектуры требует нового ADR.
```

### 9. `AGENTS.md` (корень проекта)
*Назначение: Главный манифест для всех ИИ-агентов.*

```markdown
# Инструкция для ИИ-агентов (GRACE)

## 0. Начало каждой сессии (обязательный порядок чтения)
Читай контекст экономно, в таком порядке:
1. `docs/session-log.md` — где остановилась прошлая сессия.
2. `docs/knowledge-graph.xml` — карта проекта.
3. Контракты ТОЛЬКО тех модулей, которые затрагивает текущая задача.
4. Код — только затрагиваемых модулей.

**НЕ читай весь проект целиком.** Граф существует именно для того, чтобы этого не делать.

## 1. Общие принципы
- **Код вторичен.** Сначала контракт, потом код.
- **Никогда не пиши код без `MODULE_CONTRACT`.**
- **Пайплайн:** `requirements.xml` → `technology.xml` → `development-plan.xml` → `verification-plan.xml` → `MODULE_CONTRACT` → тест → код.
- **`knowledge-graph.xml` — единственный источник правды** о структуре проекта. Добавил модуль или зависимость — сразу обнови граф. Другие документы ссылаются на модули только по ID.

## 2. Семантическая разметка
Канонический формат маркеров (используй синтаксис комментариев целевого языка):

Python:        # START: block_name  ...  # END: block_name
JS/TS/C-like:  // START: block_name ... // END: block_name

Пример (Python):

    # START: user_authentication
    def login_user(credentials):
        # START: credential_validation
        ...
        # END: credential_validation
        ...
    # END: user_authentication

Правила:
- Имя в START и END должно совпадать точно.
- Обязательна для логических блоков длиннее 50 строк.
- Вложенность допускается.

## 3. Модульные контракты (MODULE_CONTRACT)
Каждый файл в `src/` начинается с контракта, размещённого в **docstring или блочном комментарии** языка (НЕ как отдельный XML-документ — файл должен оставаться валидным кодом).

Пример для Python:

    """
    <MODULE_CONTRACT>
      <ID>M-1</ID>
      <PURPOSE>Зачем существует этот модуль</PURPOSE>
      <SCOPE>Что делает. Что НЕ делает.</SCOPE>
      <INPUTS>Входные данные: форматы, типы</INPUTS>
      <OUTPUTS>Что возвращает</OUTPUTS>
      <ERRORS>Какие ошибки выбрасывает и при каких условиях</ERRORS>
      <INVARIANTS>Условия, которые всегда истинны</INVARIANTS>
      <DEPENDENCIES>ID модулей, от которых зависит</DEPENDENCIES>
    </MODULE_CONTRACT>
    """

## 4. Управляемая автономия (PCAM)
- **Цель (WHAT):** определена в `MODULE_CONTRACT`. Не отклоняйся.
- **Границы (BOUNDARIES):** определены в `development-plan.xml`. Не выходи за них.
- **Автономия (HOW):** свободен в реализации, но только в рамках контракта и плана.
- **Если контракт кажется неверным — предложи изменение явно, не отклоняйся молча.**

## 5. Точки контроля человеком (Human-in-the-loop)
Следующие действия выполняются ТОЛЬКО после явного подтверждения пользователя:
- изменение существующего `MODULE_CONTRACT`;
- добавление новой внешней зависимости (библиотеки);
- удаление или переименование модуля;
- изменение схемы данных / формата API;
- любое действие, противоречащее `rules.md`.

## 6. Верификация
- Верификация — часть архитектуры, а не "чистка" после кода.
- Порядок: контракт → падающий тест → код → зелёный тест.
- Команды запуска — в `technology.xml`, секция `<tooling>`.
- Лог-маркеры трассировки — по `verification-plan.xml`.

## 7. Definition of Done (модуль считается готовым, когда):
1. `MODULE_CONTRACT` написан и согласован.
2. Тесты написаны и проходят (`test_command` из technology.xml).
3. Линтер не выдаёт ошибок.
4. Семантическая разметка добавлена.
5. `knowledge-graph.xml` обновлён.
6. Статус задачи в `development-plan.xml` обновлён.
7. Запись в `session-log.md` сделана.

## 8. Git-дисциплина
- Один модуль / одна задача = один коммит.
- Формат сообщения: `тип(M-X): описание` — например `feat(M-1): add credential validation`.
- **ЗАПРЕЩЕНО** коммитить при падающих тестах.
- Перед коммитом проверь well-formedness всех изменённых XML-файлов.

## 9. Самообучение (с ограничениями)
После значительной ошибки или завершения этапа обновляй `rules.md`. Правила:
- Новое правило добавляется, только если оно НЕ дублирует и НЕ противоречит существующим.
- Правило формулируется одной строкой в императиве, с указанием причины.
- Архитектурные решения фиксируй не здесь, а в `docs/decisions/` (новый ADR).
- Раз в ~10 сессий предлагай пользователю консолидацию `rules.md`.
```

### 10. `rules.md` (корень проекта)
*Назначение: "Правила, написанные кровью". Обновляется после ошибок.*

```markdown
# Жёсткие правила проекта

**Формат:** `ПРАВИЛО — причина (дата добавления)`.
Правила не дублируются и не противоречат друг другу. Противоречие — повод для консолидации.

## Базовые правила
1. **НИКОГДА** не генерируй код, если для него нет задачи в `development-plan.xml`.
2. **ВСЕГДА** начинай с `MODULE_CONTRACT`. Нет контракта — нет кода.
3. **ПЕРЕД** изменением модуля проверь его зависимости в `knowledge-graph.xml` — включая тех, кто зависит от НЕГО (`provides_to`).
4. **ОБЯЗАТЕЛЬНА** семантическая разметка для блоков длиннее 50 строк.
5. **НЕ ИСПОЛЬЗУЙ** магические числа — конфигурируемые параметры только в конфиг-файле.
6. **ЕСЛИ** реализация уходит от контракта — остановись и запроси уточнение, не импровизируй.
7. **НИКОГДА** не коммить с падающими тестами или невалидным XML.

## Правила, добавленные по ходу проекта
<!-- Добавлять сюда -->
```

### 12. `.gitignore`
Создать стандартный `.gitignore` для выбранного стека (для Python: `__pycache__/`, `.venv/`, `*.pyc`, `.pytest_cache/`; для Node: `node_modules/`, `dist/`).

### 13. `src/` и `tests/` (файлы-примеры)
- `src/main.py` (или `main.js`): содержит `MODULE_CONTRACT` в docstring (модуль `M-1`), минимальную реализацию с семантической разметкой.
- `tests/test_main.py`: минимальный проходящий тест, ссылка на `TS-1`.

---

## ФИНАЛЬНАЯ ПРОВЕРКА (выполни перед завершением)

1. Все XML-файлы синтаксически корректны (well-formed).
2. Все ID (`UC-*`, `M-*`, `T-*`, `TS-*`) согласованы между документами.
3. Модули описаны только в `knowledge-graph.xml`, остальные документы ссылаются по ID.
4. Тест из `tests/` запускается и проходит.
5. Сделана запись "Сессия 0" в `docs/session-log.md`.
6. Выполнен коммит `init: GRACE project skeleton`.

После выполнения выведи дерево созданных файлов и жди от пользователя реальных требований для заполнения `requirements.xml`.
