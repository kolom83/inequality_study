# Инструкция для ИИ-агентов (GRACE)

## 0. Начало каждой сессии (обязательный порядок чтения)
Читай контекст экономно, в таком порядке:
1. `docs/session-log.md` — где остановилась прошлая сессия.
2. `docs/knowledge-graph.xml` — карта проекта.
3. Контракты ТОЛЬКО тех модулей, которые затрагивает текущая задача.
4. Код — только затрагиваемых модулей.

**НЕ читай весь проект целиком.** Граф существует именно для того, чтобы этого не делать.

## 1. Общие принципы
- **Код вторичен.** Сначала контракт, потом код.
- **Никогда не пиши код без `MODULE_CONTRACT`.**
- **Пайплайн:** `requirements.xml` → `technology.xml` → `development-plan.xml` → `verification-plan.xml` → `MODULE_CONTRACT` → тест → код.
- **`knowledge-graph.xml` — единственный источник правды** о структуре проекта. Добавил модуль или зависимость — сразу обнови граф. Другие документы ссылаются на модули только по ID.

## 2. Семантическая разметка
Канонический формат маркеров (используй синтаксис комментариев целевого языка):

Python:        # START: block_name  ...  # END: block_name
JS/TS/C-like:  // START: block_name ... // END: block_name

Правила:
- Имя в START и END должно совпадать точно.
- Обязательна для логических блоков длиннее 50 строк.
- Вложенность допускается.

## 3. Модульные контракты (MODULE_CONTRACT)
Каждый файл в `src/` начинается с контракта, размещённого в docstring (НЕ как отдельный XML-документ — файл должен оставаться валидным кодом).

```
"""
<MODULE_CONTRACT>
  <ID>M-2</ID>
  <PURPOSE>Зачем существует этот модуль</PURPOSE>
  <SCOPE>Что делает. Что НЕ делает.</SCOPE>
  <INPUTS>Входные данные: форматы, типы</INPUTS>
  <OUTPUTS>Что возвращает</OUTPUTS>
  <ERRORS>Какие ошибки выбрасывает и при каких условиях</ERRORS>
  <INVARIANTS>Условия, которые всегда истинны</INVARIANTS>
  <DEPENDENCIES>ID модулей, от которых зависит</DEPENDENCIES>
</MODULE_CONTRACT>
"""
```

## 4. Управляемая автономия (PCAM)
- **Цель (WHAT):** определена в `MODULE_CONTRACT`. Не отклоняйся.
- **Границы (BOUNDARIES):** определены в `development-plan.xml`. Не выходи за них.
- **Автономия (HOW):** свободен в реализации, но только в рамках контракта и плана.
- **Если контракт кажется неверным — предложи изменение явно, не отклоняйся молча.**

## 5. Точки контроля человеком (Human-in-the-loop)
Следующие действия выполняются ТОЛЬКО после явного подтверждения пользователя:
- изменение существующего `MODULE_CONTRACT`;
- добавление новой внешней зависимости (библиотеки);
- удаление или переименование модуля;
- изменение схемы данных / формата API;
- любое действие, противоречащее `rules.md`.

## 6. Верификация
- Верификация — часть архитектуры, а не "чистка" после кода.
- Порядок: контракт → падающий тест → код → зелёный тест.
- Команды запуска — в `technology.xml`, секция `<tooling>`.
- Лог-маркеры трассировки — по `verification-plan.xml`.

## 7. Definition of Done (модуль считается готовым, когда):
1. `MODULE_CONTRACT` написан и согласован.
2. Тесты написаны и проходят (`test_command` из technology.xml).
3. Линтер не выдаёт ошибок.
4. Семантическая разметка добавлена.
5. `knowledge-graph.xml` обновлён.
6. Статус задачи в `development-plan.xml` обновлён.
7. Запись в `session-log.md` сделана.

## 8. Git-дисциплина
- Один модуль / одна задача = один коммит.
- Формат сообщения: `тип(M-X): описание` — например `feat(M-2): add wid api client`.
- **ЗАПРЕЩЕНО** коммитить при падающих тестах.
- Перед коммитом проверь well-formedness всех изменённых XML-файлов.

## 9. Самообучение (с ограничениями)
После значительной ошибки или завершения этапа обновляй `rules.md`. Правила:
- Новое правило добавляется, только если оно НЕ дублирует и НЕ противоречит существующим.
- Правило формулируется одной строкой в императиве, с указанием причины.
- Архитектурные решения фиксируй не здесь, а в `docs/decisions/` (новый ADR).
- Раз в ~10 сессий предлагай пользователю консолидацию `rules.md`.
